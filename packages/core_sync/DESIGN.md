# core_sync — дизайн

## 1. Выбор механизма anti-entropy

Сравнение вариантов:

| Вариант | Плюсы | Минусы | Вывод |
|---|---|---|---|
| (a) хэш-цепочки по автору + сводки по диапазонам | Простой append-only лог; компактные сводки `(count, SHA-256 ids)`; естественно ложится на HLC-диапазоны и `EventStore`; легко батчить и ограничивать backpressure | Нет явной причинности между авторами; при потере сводки нужен повторный обмен | **Выбран** |
| (b) DAG с parent-хэшами | Явная причинность, надёжное обнаружение fork | Дороже хранить/передавать; нужен обход фронта; для чата избыточен, состояние всё равно множество событий | Отклонён |
| (c) range-based set reconciliation | Эффективнее для больших расхождений | Интерактивный протокол с рекурсивным дроблением; сложнее тестировать и ограничивать по памяти | Отклонён |

Выбран (a): каждое событие содержит `prevId` — предыдущее событие **того же
автора** в группе. Это даёт проверяемую цепочку и защиту от подмены истории.
Синхронизация идёт по HLC-бакетам: `RangeDigest(fromHlc, toHlc, count,
sha256(ids))`. При несовпадении запрашивается диапазон страницами по курсору
`(hlc, id)`, поэтому память и размер ответа ограничены.

## 2. HLC и идентификатор события

`Hlc = (physicalMs, counter)`, сравнение лексикографическое. `HlcClock.tick()`
монотонен, `observe(remote)` двигает локальные часы за удалённые. Физическая
часть хранится в `EventRecord.timestamp`, счётчик — в каноническом теле.

`event.id = hex(SHA-256("opensink/sync/event-id/v1|" || canonical))`.
Каноническое тело — детерминированный protobuf (фиксированный порядок полей):
версия, groupId, channelId, authorId, HLC, kind, targetId, prevId, payload.
Подпись Ed25519 — над `"opensink/sync/event-signature/v1|" || canonical`.

## 3. Конвейер приёма

Строгий порядок: **размер → id → подпись → членство на момент события →
дедупликация → запись**.

- Размер: `payload/canonical ≤ 512 KiB`, кадр ≤ 1 MiB.
- `id` пересчитывается и сравнивается с заявленным.
- Автор — 32-байтный Ed25519-ключ; подпись проверяется через `Signer`.
- Членство: детерминированная проекция membership-событий, упорядоченных по
  `(HLC, id)`, строго до HLC события. Неизвестный автор откладывается в
  `pending` (ограниченный LRU), а не отбрасывается: membership-событие может
  прийти позже из-за разрыва. Удалённый автор получает `NotAMember`.
- `prevId`, если предыдущее событие уже известно, должно принадлежать тому же
  автору/группе и быть не новее события.
- Дедупликация — по id в памяти и в `EventStore` (`INSERT OR IGNORE`).
- Pending-события пишутся в `pending_events` (схема v7) до добавления в
  in-memory LRU. При старте `_loadGroup` восстанавливает очередь и повторно
  прогоняет конвейер, когда membership уже известен; успешно применённая
  запись удаляется из очереди. Anti-entropy остаётся страховкой, но рестарт
  больше не теряет отложенные события.

## 4. Anti-entropy

При появлении `SyncLink`:
1. высокоприоритетные `WindowRequest` для последних `N` событий каналов;
2. затем `SummaryFrame` со сводками по непустым HLC-бакетам.

Явный `requestHistory` принимает необязательный `channelId`. Фильтр входит в
`RangeRequestFrame` (поле 9), `SyncEventStore.eventsInRange` и состояние
страницы, поэтому все ответы и последующие страницы остаются в выбранном
канале. Групповой режим (`channelId == null`) сохраняется для служебных
событий и полной истории.

На несовпадение сводки отправляется `RangeRequest`; ответ — `EventsFrame`
(≤ `maxBatchSize`, например 64) с курсором и `more`. Следующая страница
запрашивается только после применения текущей (backpressure). Исходящая
очередь ограничена, low-priority кадры отбрасываются при переполнении;
anti-entropy повторит их при следующем обмене.

## 5. Gossip и защита от штормов

Новые события рассылаются соседям как `GossipFrame(events, hops)`. Защита:
дедупликация по id на входе, не пересылаем обратно источнику, `hops ≤ 4`,
per-session LRU отправленных id, token bucket на gossip, лимит размера
исходящей очереди. События, полученные anti-entropy, тоже распространяются
gossip-ом. Anti-entropy остаётся страховкой при потерях.

## 6. Приоритетная загрузка и tombstones

Последние `N` сообщений канала запрашиваются первыми (high-priority lane).
Остальная история догружается диапазонами в low-priority lane; UI может
запросить окно канала отдельно через `loadChannelWindow`.

Правки/удаления — отдельные события `messageEdited`/`messageDeleted` с
`targetId`. Исходное событие не мутируется. `GroupProjection` применяет
tombstone-ы после создания сообщений, поэтому порядок доставки не влияет на
итоговое состояние. Редактировать/удалять может только автор сообщения.

## 7. Приёмка и ограничения

- 36 тестов core_sync, включая 1000 детерминированных прогонов симулятора
  с N=3, реальным Ed25519, случайным порядком, потерями и разделами сети,
  а также три e2e-теста `SyncEngineImpl` поверх `DriftEventStore` (VM и
  Chrome/dart2js).
- `dart analyze packages/core_sync` — чисто.
- Ограничения: `prevId` не проверяется на «непосредственного предшественника»
  при отсутствии промежуточных событий; `HlcValidator.maxClockSkewMs`
  применяется только к будущим HLC; прошлые метки не ограничиваются
  (решение poll).
- `ProtoReader`/`ProtoWriter` используют арифметику вместо 32-битных
  битовых операций: dart2js иначе обрезал HLC/таймстемпы (~1.7e12). Это
  выявлено Chrome-прогоном e2e и закрыто тестом `core_protocol/test/wire_test.dart`.
- Предположение: `GroupCreated` делает участником только автора; остальные
  участники добавляются отдельными `MemberAdded` (initialMembers в payload
  не парсится). Группы регистрируются приложением через `registerGroup`.


## 8. Решения poll (2026-10-23)

| Вопрос | Решение |
|---|---|
| Членство при `GroupCreated` | Участник — только автор; остальные — отдельные `MemberAdded` |
| HLC clock skew | Отклонять только будущие метки > `maxClockSkewMs` (30 с) |
| Pending membership | Персистентная очередь в `pending_events` (v7) + in-memory LRU; после рестарта восстанавливается и применяется при появлении membership |
| Ширина HLC-бакета сводок | Фиксированная константа протокола `syncSummaryBucketMs = 60 s` |
| История старше окна | Только по явному `requestHistory` (UI); автоматически — самый свежий расходящийся диапазон |
| Права edit/delete | Только автор сообщения |
| Проверка event id | Только в `core_sync` до `EventStore.write` |
| Подпись в 1000 прогонах | Реальный Ed25519 (ключи кэшируются между прогонами) |
| Backpressure | Одна страница на диапазон + лимит исходящей очереди |
| Обнаружение групп | Явный `registerGroup` приложением |
