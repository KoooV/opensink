# core_group — дизайн

## 1. Назначение

`core_group` — чистая проекция административных событий группы. Состояние группы
зависит только от множества событий, а не от порядка доставки. Подпись и проверка
конверта выполняются в `core_sync` до вызова проекции; здесь проверяются инварианты
события, членство и права автора.

## 2. События

- `GroupCreated` — имя, владелец, начальные участники.
- `InviteIssued` — инвайт: `inviteId`, режим (`open`/`approval`), лимит
  использований, срок, relay hint.
- `MemberJoined` — вход по инвайту; автор — сам входящий. Несёт
  `inviteProof` — HMAC секрета инвайта; без валидного proof вход отклоняется.
- `MemberApproved` — подтверждение входа админом/владельцем.
- `MemberAdded`/`MemberRemoved` — прямое управление составом.
- `RoleSet` — назначение роли (кроме `owner`).
- `ChannelCreated`/`ChannelDeleted` — каналы и минимальные роли просмотра/постинга.
- `GroupRenamed`, `OwnerTransferred`, `KeyRotated`.

Роли: `owner > admin > moderator > member`. Владелец неприкосновенен: его нельзя
удалить или понизить, передача владения — только отдельным `OwnerTransferred` от
текущего владельца.

## 3. Права

| Действие | Кто может |
|---|---|
| Инвайты, подтверждение входа | owner, admin |
| Кик | owner, admin, moderator; ранг автора ≥ ранга цели; не владельца |
| `RoleSet` | owner, admin; цель не владелец; нельзя менять свою роль; новая роль ≤ ранга автора |
| Каналы | owner, admin |
| `KeyRotated` | owner, admin |
| Переименование | owner, admin |
| Передача владения | только текущий owner |

Просмотр/постинг в канале — по `minViewRole`/`minPostRole` из `ChannelCreated`.
Права проверяются на состоянии, построенном из событий, которые строго раньше
проверяемого в детерминированном порядке.

## 4. Конфликты

После `GroupCreated` (он всегда применяется первым как корень истории) порядок
топологический: ребёнок не раньше `prevId`, а среди доступных событий
выбирается меньший `(timestamp, counter, event.id)`. Корень можно зафиксировать
через `expectedGroupId`/`genesisEventId`, чтобы чужое или поддельное создание
не перехватило проекцию.

У каждого автора проверяется цепочка `prevId`: родитель существует, принадлежит
тому же автору/группе и имеет не больший HLC. Форк детей одного `prevId`
разрешается детерминированно меньшим HLC-валидным ребёнком; несколько
независимых корней автора отбрасывают его цепочку. `GroupController` хранит
журнал событий и пересчитывает проекцию при каждом `apply`, поэтому порядок
доставки и форки сходятся к `fromEvents`. `apply` сдвигает курсор автора даже
при семантическом отказе, чтобы следующие события цепочки не терялись.
Дубликаты одного id с разными телами разрешаются выбором стабильно меньшего
канонического тела внутри группы; для genesis выбирается меньший валидный
вариант. События чужих `groupId` отбрасываются до дедупликации. Прямой `apply`
при другом теле уже обработанного id возвращает `EventIdCollision`, а
контроллер выбирает каноническое тело из журнала.

`core_group` получает из `core_sync` уже проверенные события с
`id == SHA-256(canonical body)`; правило выбора тела — защита от дубликатов,
а не замена проверке идентификатора.

`appliedEventIds` и fingerprints содержат только события, прошедшие проверку
цепочки (включая семантические отказы и no-op); orphan/форк-проигравшие не
помечаются применёнными. Публичная фабрика `GroupState` требует согласованные
`cursors`/`eventFingerprints` для непустого `appliedEventIds`.

`GroupController` ограничивает журнал (`maxJournalEvents`), сериализует
конкурентные `apply`, отклоняет `StateRegression` (откат эпохи ключа) и
атрибутирует ротацию событию, реально поднявшему эпоху. Семантически
отклонённое, но структурно валидное событие остаётся в журнале: результат
`apply` считается по replay, а не по инкрементальному состоянию.

При сериализации `GroupState` сохраняются `genesisEventId`, курсоры цепочки
авторов и fingerprints тел; при загрузке состояние продолжает проверять
`prevId`.

- Владелец не может быть удалён или понижен ни при каком порядке.
- Конкурентные действия равных ролей разрешаются меньшим `(hlc, id)`: событие,
  которое идёт первым, применяется; следующее проверяется на уже изменённом
  состоянии. Поэтому при взаимных киках побеждает автор события с меньшим
  `(hlc, id)`, а второй кик отклоняется как действие неудалённого участника.
- Кик против смены роли: если смена роли идёт раньше, кик проверяется против новой
  роли; если кик раньше — смена роли для удалённого участника отклоняется. Итог
  одинаков при любом порядке доставки, потому что порядок вычисляется из событий.
- Отклонённое по смыслу или no-op событие не меняет содержимое; его id
  помечается применённым, если цепочка валидна. События, не прошедшие проверку
  цепочки (orphan, backdated, форк-проигравший), не помечаются применёнными.

## 5. Инвайты и утечка ссылки

Ссылка содержит `groupId`, `inviteId`, `group_secret`, публичный ключ инвайтящего
и relay hint; `group_secret` не попадает в `toString()`.

- Вход требует `inviteProof` = HMAC(`inviteProofMessage`, `invitationKey` из
  `group_secret`). Проверка инжектируется как `InviteProofVerifier`; одного
  публичного `inviteId` недостаточно. Реальный HMAC считается в приложении,
  в тестах используется `InMemoryInviteProofVerifier`.
- `open`: вход сразу, но обязателен хотя бы один ограничитель — лимит
  использований или срок. Утечка ссылки позволяет любому входить до исчерпания
  лимита/срока; для чувствительных групп нужен approval.
- `approval`: вход создаёт заявку, участник добавляется только после
  `MemberApproved` админа/владельца. Утечка не даёт членства без подтверждения,
  но раскрывает `group_secret` (тему signaling); секрет нужно считать
  скомпрометированным и ротировать групповые ключи.
- Просроченный или исчерпанный инвайт отклоняется. Заявка на `approval` не
  расходует использование до подтверждения.

## 6. Ротация ключей

Успешное удаление участника увеличивает `keyEpoch`. `KeyRotated` позволяет
админу/владельцу задать эпоху вручную (только вперёд). `GroupController` при
изменении эпохи отдаёт новый пакет ключа в `GroupKeyDistributor`; реализация
рассылает его по E2E-зашифрованным личным сообщениям только оставшимся
участникам. В тестах используется `InMemoryGroupKeyDistributor`.

## 7. Решения poll (2026-10-24)

| Вопрос | Решение |
|---|---|
| Проверка подписи | Только в `core_sync` на уровне `Envelope`; `core_group` получает проверенные события |
| Новые события в `SyncEventKind` | Добавить следующим шагом, вместе с каноническим форматом |
| Раздача sender keys | Оставить интерфейс и fake; E2E-доставка — вне `core_group` |
| Срок инвайта | Проверять по HLC-времени события; clock skew — в `core_sync` |
| Legacy `GroupState` | Мигрировать потребителей на `core_group.GroupState` и убрать старый |
| Монотонность HLC цепочки | Неубывающий HLC; равный допустим |
| Дубликат `id` с разными телами | Детерминированный выбор меньшего канонического тела внутри группы; прямой `apply` возвращает `EventIdCollision`, контроллер пересчитывает журнал |
| Корень группы | `expectedGroupId` и `genesisEventId` обязательны |
| Форк в `GroupController` | Журнал событий и повторный детерминированный пересчёт; опоздавшие и форки сходятся к `fromEvents` |
| Журнал `GroupController` | Лимит `maxJournalEvents`, `JournalFull` при переполнении, конкурентные `apply` сериализуются |
| Результат `apply` в контроллере | Считается по replay; семантический отказ не откатывает журнал, `Err` — для детерминированно невалидных тел |
| Откат эпохи из-за позднего форка | `StateRegression`: событие не коммитится, ключ не откатывается |
| Атрибуция ротации | Событие, реально поднявшее эпоху; чужой `keyPackage` не переиспользуется |
| Сериализация `GroupState` | Требовать согласованные `genesisEventId`, `appliedEventIds`, курсоры и fingerprints при восстановлении |
| HMAC инвайта | `InviteProofVerifier`; адаптер `GroupInviteProofVerifier` в `apps/app` |
| Бэкдейтинг первого join | Принятый риск; trusted time/DAG — в `docs/OPEN_QUESTIONS.md` Q36 |

## 8. Критерии приёмки

1. Любая перестановка одного множества событий даёт идентичный `GroupState`.
2. Роли и права проверяются по причинному состоянию; запрещённые действия
   отклоняются без изменения содержимого (курсор цепочки автора сдвигается).
3. Владелец не удаляется и не понижается; владение меняется только передачей.
4. Конфликты разрешаются по `(hlc, id)`; взаимные кики и кик против смены роли
   сходятся к одному результату.
5. `open` и `approval` инвайты соблюдают срок/лимит; заявка не даёт членства до
   подтверждения.
6. Удаление участника повышает эпоху и распределяет новый ключ только оставшимся
   через fake-распределитель.
7. Права на каналы и инварианты событий проверяются тестами.
8. Цепочка `prevId` и монотонность HLC автора проверяются; `fromEvents` и
   `GroupController` сходятся при форке и любом порядке доставки.
9. Корень группы фиксируется `expectedGroupId`/`genesisEventId`; дубликаты id
   с разными телами дают детерминированный результат, прямой `apply` сообщает
   `EventIdCollision`.
10. `MemberJoined` без валидного `inviteProof` не даёт членства.
11. Журнал контроллера ограничен, конкурентные `apply` сериализованы, поздний
    форк не откатывает `keyEpoch`, а снапшот с несогласованными полями
    отклоняется.
