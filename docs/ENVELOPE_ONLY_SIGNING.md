# Дизайн: подпись только на уровне Envelope (core_group / core_media)

## Статус
Чернота (проектное решение, требует утверждения)

## Контекст
Принцип №3 проекта: «Любое событие, влияющее на состояние группы, подписано Ed25519 и валидируется до применения. Состояние группы — чистая функция от множества событий.»

В текущей реализации (`core_domain/src/events/group_event.dart`) у `GroupEvent` есть метод `toCanonicalMap()` и комментарий, что подпись события носится на уровне `Envelope`. Это создаёт неясность:
- подписывается ли само доменное событие отдельно?
- кто отвечает за верификацию — `core_group`, `core_sync`, или уровень протокола (`core_protocol`/`Envelope`)?
- как `core_media` (звонки, экран) вписывается в эту модель, если медиа-события не являются групповыми событиями `GroupEvent`?

## Решение
**Подпись Ed25519 накладывается только на бинарный `Envelope` (protobuf-конверт) в `core_protocol`. Доменные события `GroupEvent` и медиа-события не подписываются отдельно.**

Доверие устанавливается подписью конверта, а не полями внутри события. Поля события валидируются инвариантами (`validateInvariants`) после вскрытия конверта, но криптографическая авторизация — на уровне конверта.

### Зона подписи (`Envelope.signatureData()`)
Подписываются поля заголовка (1–4): `version`, `type`, `sender` (Ed25519 public key), `hlc` + `payload` (сериализованное вложенное сообщение). Сам `signature` в зону подписи не входит (циклическая зависимость). `unknownFields` — не в зоне подписи (релеи могут добавлять маршрутную метаданные без инвалидации).

### Поток данных core_group
1. Узел создаёт `GroupEvent` (например, `GroupCreated`).
2. Событие сериализуется в `payload` (protobuf, см. `core_protocol`).
3. Собирается `Envelope{type: groupEvent, sender: peerId.publicKey, hlc: now, payload, signature}`.
4. `signature = Ed25519.sign(envelope.signatureData(), privateKey)`.
5. `Envelope` отправляется через `SignalingChannel` / `Transport` / `Relay`.
6. Получающий узел: верифицирует `Envelope.signature` через `Signer.verify(envelope.signatureData(), signature, sender)` → при неудаче отбрасывает.
7. Декодирует `payload` в `GroupEvent`, вызывает `GroupEvent.validateInvariants()` → при неудаче отбрасывает.
8. Применяет `Group.apply(event)` — чистая функция, состояние обновляется.

### core_media (звонки, экран, топологии)
Медиа-события (начало звонка, offer/answer SDP, ICE-кандидаты, запрос на демонстрацию экрана) **не являются `GroupEvent`**. Они не меняют состояние группы и не попадают в лог событий `core_sync`.

Поток для медиа:
1. `core_media` создаёт сигнальное сообщение (SDP, кандидаты, контроль медиа).
2. Сериализует в `payload`, собирает `Envelope{type: mediaMessage, ...}`.
3. Подписывает на уровне `Envelope` (тот же `Signer`).
4. Доставка через `PeerLink` (прямой WebRTC data channel) или `Relay`.
5. Получающий узел верифицирует подпись конверта, затем декодирует медиа-сообщение.

Медиа-сообщения не требуют `Group.apply` и не являются частью логически склеенного состояния группы. Они аутентифицированы подписью отправителя на уровне конверта.

### Границы ответственности

| Слой | Отвечает за |
|------|-------------|
| `core_domain` | Модели `GroupEvent`, `validateInvariants()`, чистая функция `Group.apply`. Не знает о `Envelope` и подписях. |
| `core_protocol` | `Envelope`, `signatureData()`, сериализация/десериализация protobuf. Не верифицирует подпись (нет ключей). |
| `core_crypto` | `Signer` (Ed25519 sign/verify), `SecureKeyStore`. |
| `core_sync` | Приём `Envelope`, верификация подписи через `Signer`, вызов `validateInvariants`, `Group.apply`, запись в `EventStore`. |
| `core_group` | Бизнес-логика прав, ролей, каналов (в будущем). Никакой криптографии. |
| `core_media` | Создание медиа-конвертов, топологии, звонки. Подпись — через общий `Signer` на уровне `Envelope`. |
| `platform_*` | Реализация `Signer` нативной криптографией (Android Keystore, libsecret, Web Crypto). |

## Что НЕ делается
- ❌ Отдельная подпись полей `GroupEvent` (id, timestamp, name и т.п.) — избыточно, конверт уже подписан.
- ❌ Подпись медиа-потоков (SRTP/SRTCP) на уровне приложения — WebRTC обеспечивает шифрование транспорта.
- ❌ Доверие к `unknownFields` конверта — они не в зоне подписи, не влияют на доставку.

## Риски
- Релеи могут подменять `unknownFields` без инвалидации подписи. Допустимо: неизвестные поля не используются для решений о доставке (ADR-001, п. «unknownFields»).
- Если `sender` в конверте подменяется вместе с переподписью — защита возможна только через верификацию `sender` против известной личности/PeerId в `core_sync`. Это вне зоны подписи конверта.

## Критерии приёмки
- `core_group` не импортирует `core_crypto` и не вызывает `Signer.sign/verify` напрямую.
- `core_media` не вызывает `Group.apply` и не создаёт `GroupEvent`.
- Все входящие `Envelope` верифицируются на подпись перед декодированием `payload` (в `core_sync`).
- `GroupEvent.validateInvariants()` вызывается после вскрытия конвектора, до `Group.apply`.
- Тесты: `core_sync` отбрасывает `Envelope` с неверной подписью; `core_group` применяет только валидные события.
