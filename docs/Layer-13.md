Слой: core_media, hosted-топология.

Сначала design doc с честной оценкой: в flutter_webrtc и браузерах нет пересылки RTP «как есть». Варианты: (а) пересылка remote-трека через addTrack в другие соединения (декод + повторное кодирование, дорого для видео); (б) аудио-микшер (один смешанный поток на участника); (в) encoded transform / insertable streams на web, где применимо. Оцени стоимость CPU/аплинка каждого и выбери стратегию отдельно для аудио и видео экрана.

Задача:
1. Оценка кандидатов: capabilities (платформа, ядра, питание от сети, измеренный аплинк через пробы, uptime). Явное согласие пользователя быть кандидатом.
2. Детерминированные выборы: все пиры вычисляют лидера из одного набора подписанных capabilities; sticky-лидер с гистерезисом против флапов.
3. LeaderLease: подписанная аренда с номером эпохи; при конфликте побеждает большая эпоха, при равенстве меньший PeerId.
4. Переключение топологии: mesh при малом числе участников, hosted при превышении порога по участникам или аплинку.
5. Резервный лидер (second best) заранее держит соединения; при потере лидера переход за целевое время X секунд; если кандидатов нет — откат в mesh с ограничением.
6. Защита лидера: порог CPU/аплинка → деградация (убрать видео, снизить разрешение, ограничить зрителей).
7. В UI должно быть видно, кто хостит, и можно отказаться.

Тесты: симуляция выборов с разделениями сети, флапами и одновременным падением лидера и запасного.
Приёмка: звонок на 12 участников держится на hosted-топологии, смерть лидера восстанавливается за целевое время, экран остаётся доступен ограниченному числу зрителей.
